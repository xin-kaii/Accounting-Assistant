## 四、已经做出的取舍（这个最有说服力）

<!-- 已经发生的取舍，现在就填，别等第 13 天 -->

### 取舍 1：不单独维护接口文档，约定写在代码里

- **本来打算**：写一份 `docs/02-数据契约.md`，四个函数签名 + 三张表 + 返回格式，约 260 行
- **为什么改**：写完后核对发现，它 90% 的内容和 `schema.sql` 的注释、函数 docstring 完全重复。四个人真正会打开的是代码，不是文档；而文档一旦和代码不同步，比没有更糟
- **最终做法**：约定写在 `schema.sql` 注释、函数签名和 docstring 里。第 2 天的任务从"写文档"改成"四个人一起核对代码接口"
- **代价**：答辩时少了一份可以展示的"接口文档"，需要口头解释这个决定

### 取舍 2：OCR 用视觉大模型，不自己搭识别流程

- **本来打算**：Tesseract 做 OCR，再写规则抽字段
- **为什么改**：中文小票版式乱、字体杂、还有手写，传统 OCR 抽字段准确率撑不住演示，而且要写图像预处理（灰度、去噪、二值化），零基础团队至少要 3 天
- **最终做法**：图片直接交给视觉大模型，一次调用返回结构化 JSON，成本约几毛钱
- **代价**：依赖网络和 API 额度；识别率仍然有限，所以保留"识别 → 人工确认 → 入库"的流程作为兜底

## 小提示

**"没做完"不扣分，"说不清为什么没做完"才扣分。**

评审最反感的是：README 里写"已完成"，评审一试发现跑不通。
最认可的是：文档里明确写"这项只做了 A 部分，B 部分因为 X 没做，降级方案是 Y"。
