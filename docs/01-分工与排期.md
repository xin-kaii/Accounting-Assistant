## 0. 先说清楚：我们到底要交什么

考核方收到我们的东西之后，会这么做：

1. 把我们的 GitHub 仓库下载下来
2. **照着我们的 README，一步一步敲命令**
3. 打开网页，输入"午饭 25"，看是不是真的记上了
4. 点开提交记录，看是不是几个成员在 15 天里一点点做出来的
5. 答辩时问每个人："你负责哪块？为什么这么做？"

所以要交的东西是 5 样：

| 交付物 | 大白话 | 谁负责 |
|---|---|---|
| 一个能点开的网页应用 | 不是 PPT，不是文档，是打开浏览器能用的东西 | A / B / C（A 汇总成一条能演示的流程） |
| 公开的 GitHub 仓库 | 代码放网上，谁都能下载 | A |
| README.md | 一份说明书，让陌生人 15 分钟内跑起来 | **每人写自己那段，A 统稿** |
| 示例数据 | 预置好的 100 多条账单，评审不用自己造 | **C** |
| Dockerfile | 打包成一个"一键运行"的东西，不用装 Python | **A**（第 5 天出第一版） |
| 答辩 PPT | 讲我们做了什么、怎么做的 | **每人交 3 页，B 合并** |

**一句话总结**：交的不是"我们想做什么"，而是"**你能亲手跑起来的东西**"。

## 1. 四个必做功能（题目原话 → 大白话）

题目给了 4 项，**至少要做成 3 项**。我们把 4 项全做。

| 题目原话 | 大白话 | 做完是什么样 |
|---|---|---|
| ① 自然语言记账 + 小票/截图 OCR 录入 | 用户打一句话"午饭 25"，系统自动认出金额和类别；用户拍张照片，系统从图里读出金额 | 输入框打字 → 屏幕上弹出一张卡 → 点确认 → 记上了 |
| ② 消费自动分类与统计 | 每笔钱自动归到"餐饮/交通/购物"里；能按类别、按月算总数 | 一个饼图，显示这个月吃饭占 40% |
| ③ 自然语言查账 | 用户问"我上个月吃饭花了多少"，系统真的去数据库里算，而不是瞎编 | 输入问题 → 屏幕上出现一个真实数字 + 明细 |
| ④ 预算设定与超支提醒 | 给某类或总额设个月度上限，快超的时候提醒 | 一根进度条，超了变红 |

**加分项（有余力再做）**：月度对比、异常支出提示、信息不全时反问用户、拒绝"帮我找贷款口子"这类越界请求、薄薄一层 REST 接口（见 5.5）。

## 2. 心理准备：零基础 15 天是什么体验

说实话，会有这几种时刻：

- **装环境卡一整天**。别人一句 `pip install`，你报了一屏红字。
- **报错看不懂**。`ModuleNotFoundError`、`CORS`、`KeyError`……
- **看别人的代码像天书**。这很正常，第 3 天就好了。
- **改一个地方，另一个地方坏了**。
- **第 8 天左右会怀疑自己**。这是所有人的必经阶段，挺过去就顺了。

三条建议，比技术更重要：

1. **AI 可以帮你写代码，但你必须能读懂每一行。** 答辩会问实现细节，答不上来会扣分。看不懂就让 AI 用大白话解释一遍。
2. **卡住超过 2 小时，立刻喊人。** 自己磨 6 小时的坑，别人 10 分钟就能解决。
3. **先跑通，再优化。** 端到端流程没通之前，不要调模型效果、不要美化界面。

**时间投入**：建议每人每天 4 小时左右（晚上 7-11 点 + 周末白天）。
原本 4 人 × 15 天 ≈ 240 小时；现在实际是 **3 人 × 14 天 ≈ 168 小时**，少了约 30%。
**这就是为什么砍掉三个加分项**——不砍，一定做不完。

### 3.3 为什么这么分？

**不是按"前端/后端"分，是按"功能"纵向分。**

如果按前后端分：
```
C 做前端 → 等 A 把接口写完 → 结果 A 卡住了 → C 干等三天
```
如果按功能分：
```
C 负责"从图片到数据"这一整条 → 自己就能从头做到尾 → 不用等谁
```

每个人手里都有一条"能独立跑通"的链路，这是三个人能并行、不互相阻塞的唯一办法。

**那为什么页面不集中给一个人？**

因为纵向切有个副作用：**页面会全压在一个人身上**。
5 个 Streamlit 页面 + README + PPT，零基础 15 天做不完。所以做了两层拆分：

```
纵向：A 数据 / B AI / C 图片（+ 记账页账单页）   ← 每个人能独立跑通
横向补丁：
  - 统计页、预算页 → A 自己写（get_stats / check_budget 都是他产的数据）
  - 对话页        → B 自己写（parse_query 是他产的数据）
  - 记账页、账单页 → C 写（主链路最早要通，且他需要这两个页面验证 OCR 结果）
  - README 每人写自己那段 → A 统稿
  - PPT 每人 3 页 → B 合并
```

**结果**：没有人同时扛"5 个页面 + 全部文档 + 全部 PPT"。
每个人写的页面都是自己最熟的那个函数，不用来回问"你返回什么结构"。

> 这条原则叫「**谁产数据谁画页面**」。
> 11 月 22 日 D 住院后，五个页面就是按这个原则分掉的，见 3.2 节的「任务转移」。

## 5. 第一步：先把"记账本的表格"定下来

### 为什么先定这个

想象 3 个人一起记账，但每个人用的记账本格式不一样：
- A 写"25 元，餐饮，2026-11-20"
- B 写"25，吃饭，昨天"
- C 写"金额 25.0，类别 food，日期 2026/11/20"

**这就乱套了。** 所以在写任何代码之前，三个人必须先统一"表格长什么样"。
这个约定叫"**数据契约**"，意思是"我们三个人的约定，谁都不许赖账"。

> **约定写在哪？就写在代码里，不另建文档。**
> - 表结构 → `app/db/schema.sql` 的注释（每个字段为什么这么设计都写着）
> - 函数签名 → 每个 `def` 本身
> - 返回格式 → 每个函数的 docstring（里面有完整的 JSON 例子）
>
> 好处很实在：改代码时约定一定会跟着改，不会出现"文档说一套、代码做一套"。
> 第 2 天要做的不是写文档，而是**三个人一起把这三个文件看一遍**。

### 三张表

**表 1：账单表（最重要）**

| 列名 | 存什么 | 例子 |
|---|---|---|
| id | 编号，自动生成 | 1 |
| occurred_at | **钱是什么时候花的** | 2026-11-20 12:30 |
| amount | 金额，**单位是「分」** | 2500（= 25.00 元） |
| direction | 是支出还是收入 | expense |
| category | 一级分类 | 餐饮 |
| subcategory | 二级分类（可为空） | 快餐 |
| merchant | 商户（可为空） | 沙县小吃 |
| note | 备注（可为空） | 和同事AA |
| source | 从哪进来的 | text / receipt / manual |
| raw_input | 用户原话，用于排查 | "午饭25，和同事AA" |
| confidence | 识别置信度（可为空） | 0.92 |
| created_at | **这条记录是什么时候存进来的** | 2026-11-20 12:35 |

> ⚠️ `occurred_at`（花钱的时间）和 `created_at`（存进来的时间）**必须是两个字段**。
> 因为用户可能今天补记昨天的账，这两个时间就不一样。答辩时这是个好问题。

> 💰 **金额约定（3 个人都要记住，写在 `app/money.py` 里）**
> - **数据库里存「分」**：25 元存成 `2500`
> - **B 和 C 返回给界面的还是「元」**：`{"amount": 25.0}`，因为模型和用户都用元说话
> - **A 入库时**用 `money.to_cents()` 转成分，**出库时**用 `money.to_yuan()` 转回元
> - 业务代码里**不许手写 `*100` / `/100`**，一律调 `app/money.py`
>
> 为什么费这个劲：浮点数累加会出现 `0.1+0.2=0.30000000000000004`，
> 统计 120 笔之后"刚好花完 800 元"可能被判成"还没超支"，而这个边界是要在答辩上讲的。

> 🔍 **还有两个字段谁填，先说清楚**
> - `source`（`text` / `receipt` / `manual`）由**写页面的人**在调 `add_transaction` 时传
> - `raw_input`（用户原话）同上；拍照进来的可以存 OCR 原文，也可以存 None
> - 不传的话会落到默认值 `source=manual`，所有账都被标成手动录入，答辩讲"数据来源"就对不上

**表 2：预算表**

| 列名 | 存什么 | 例子 |
|---|---|---|
| id | 编号 | 1 |
| month | 哪个月 | 2026-11 |
| category | 哪个类别（**空 = 总预算**） | 餐饮 |
| amount | 上限多少钱 | 800 |

**表 3：修正记录表**（用来"越记越准"，可选但很加分）

| 列名 | 存什么 | 例子 |
|---|---|---|
| id | 编号 | 1 |
| raw_input | 用户原话 | "塔斯汀25" |
| wrong_json | AI 最初认错的 | {分类: 其他} |
| correct_json | 用户改成的 | {分类: 餐饮/快餐} |
| created_at | 什么时候改的 | 2026-11-20 |

> 这张表怎么用：下次 AI 再遇到"塔斯汀"，把历史修正记录作为例子塞进 prompt，它就不会再认错了。
> **就 20 行代码，答辩时是个实打实的亮点。**

### 5.5 ~~加分项：薄薄一层 REST 接口~~

> ⛔ **11 月 22 日已砍掉。** D 住院后 3 个人要干 4 个人的活，这个加分项不再做。
> 下面的内容保留作参考，**不列入任何人的日程**。如果到第 12 天还有余力再考虑。

**做法**：把已有的 3 个函数包一层 HTTP，不重写任何业务逻辑。

```python
# app/api.py  —— 大概 40 行
from fastapi import FastAPI
from app.services.ledger import add_transaction
from app.services.stats import get_stats
from app.services.query_parser import parse_query

app = FastAPI()

@app.post("/transactions")
def api_add(payload: dict):
    return {"id": add_transaction(payload)}

@app.get("/stats")
def api_stats(start: str, end: str, category: str = None):
    return get_stats(start, end, category)

@app.post("/query")
def api_query(payload: dict):
    return parse_query(payload["question"])
```

启动：`uvicorn app.api:app --port 8000`，然后打开 `http://127.0.0.1:8000/docs` 就能看到三个接口。

**三条纪律**：
1. **主线不变**。Streamlit 页面继续**直接调函数**，不改成走 HTTP。改了就多一层故障点，还会拖慢 D。
2. **API 是"额外再暴露一层"**，不是替换。
3. **最多 40 行**。如果写着写着超过 100 行，说明跑偏了，停手。

**答辩话术（背下来）**：
> "我们主链路是**端到端纵向负责**，保证零基础团队 4 个人能并行、不互相阻塞；
> 同时额外暴露了一层 REST 接口，方便后续前后端分离或第三方调用。
> 主链路不依赖这一层，它挂了主流程照常跑。"

这句话既解释了团队协作方式，又展示了工程视野。**只花半天，是这份文档里性价比最高的加分项。**

## 7. 新手必懂的 12 个词

| 词 | 大白话 | 我们哪里用到 |
|---|---|---|
| **仓库（repo）** | 放代码的网上文件夹 | GitHub 上那个 |
| **commit（提交）** | 存一次档 | 每天至少存一次 |
| **分支（branch）** | 自己另开一个副本改，不影响别人 | `feat/记账-A` |
| **合并（merge）** | 把自己的副本并回主线 | 每天 21:00 |
| **虚拟环境（venv）** | 给这个项目单独装的一套 Python 库，不和电脑上别的打架 | 第 1 天就要建 |
| **依赖** | 项目要用到的第三方库 | 写进 `requirements.txt` |
| **`.env` / 环境变量** | 存密码和密钥的文件，**绝对不能传上网** | 存 API Key |
| **API** | 别人的程序提供的服务，你调它、它给你结果 | 调大模型靠它 |
| **API Key** | 调 API 的密码 | 找供应商申请 |
| **JSON** | 一种数据格式，长得像 `{"金额": 25}` | 模型返回的东西 |
| **SQLite** | 一个数据库文件，不用装服务器 | 存账单 |
| **Docker** | 把整个运行环境打包，别人电脑上一键跑 | 第 5 天出第一版 |

## 8. Git 怎么用（照着敲）

### 第一次配置（只做一次）

```bash
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"
```

### 每天固定动作

```bash
# 1. 开工前，先把主线的更新拉下来
git checkout main
git pull

# 2. 切到自己的分支（第一次要 -b 新建，之后直接 checkout）
git checkout -b feat/记账-A

# 3. 干完活，看看改了啥
git status
git diff

# 4. 提交
git add .
git commit -m "feat(ledger): 加了一笔账单能存进数据库"

# 5. 推上去
git push origin feat/记账-A

# 6. 第二天想同步主线的改动
git checkout main
git pull
git checkout feat/记账-A
git merge main
```

### 提交信息怎么写

格式：`类型(模块): 这次做了什么`

```
feat(ledger): 加了一笔账单能存进数据库
fix(ocr): 修好了小票金额识别为 0 的问题
docs(readme): 补充 Docker 启动步骤
test(stats): 加了按月统计的 3 个测试
```

类型就这四个够用了：`feat`（新功能）/ `fix`（修 bug）/ `docs`（文档）/ `test`（测试）。

### 每天 21:00 的合并流程（A 操作，15 分钟）

```bash
git checkout main
git pull
git merge feat/记账-A
git merge feat/ai-B
git merge feat/界面-C
git merge feat/ocr-C
# 有冲突就当场解决，解决完 push
git push origin main
```

**冲突了怎么办**：别慌，打开文件找 `<<<<<<<` 标记，两个人商量留哪个，删掉标记，再 `git add` + `git commit`。

### `.gitignore` 必须包含

```
.venv/
__pycache__/
*.pyc
.env
data/*.db
*.log
.idea/
.vscode/
.DS_Store
```

### 出错了怎么办

| 情况 | 怎么办 |
|---|---|
| 提交了不该提交的文件 | 群里喊 A，别自己乱改历史 |
| 合并冲突解决不了 | 两个人一起看，别一个人硬扛 |
| 想把没提交的改动全扔掉 | `git checkout .`（**慎用，改了就没了**） |
| 不确定自己在哪个分支 | `git branch` |

## 9. 会踩的坑

| 坑 | 表现 | 怎么躲 |
|---|---|---|
| **API Key 传上网** | 仓库里出现 `sk-xxx` | `.env` 写进 `.gitignore`；提交前扫一遍 |
| **`.env` 文件被提交** | 别人 clone 下来能看到你的 Key | 只提交 `.env.example`（里面是 `sk-你的key`） |
| **缓存文件被提交** | `__pycache__/`、`.pyc` 出现在仓库里 | `.gitignore` 加上 |
| **数据不持久化** | 刷新网页，账单全没了 | 必须有 SQLite，不能用 `st.session_state` 存数据 |
| **SQLite 并发写报错** | `database is locked` | 每次操作开新连接，用完立刻关 |
| **模型返回的 JSON 坏了** | `json.loads` 报错 | 用 `try/except` + 重试一次 + 正则兜底 |
| **中文乱码** | 文件全是 `????` | 所有文件存成 UTF-8 编码 |
| **别人电脑跑不起来** | 在自己电脑好好的 | 第 13 天找"陌生人"按 README 试一遍 |
| **??????** | 第 8 天还有 3 个页面是空的 | 启动 3.2 的降级预案：5 个页面并成 3 个 |
| **A 被杂活堵住** | 第 9 天业务函数还没写完 | Dockerfile 第 5 天就做第一版；合并固定 21:00 |
