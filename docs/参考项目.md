🔗 https://github.com/KuGua-Gu/gduf-ai-assistant

**他们已经做完的**：Agent 核心（意图路由、草稿确认、异常兜底）、`mock_llm.py` 离线模式、业务层落库（账单/统计/预算 + SQLite）、契约先行（`docs/api-contract.md` + `Protocol`）、71 个测试通过、GitHub Actions。

**他们自己承认的缺口**（README 原文）：

| 缺口 | 原文 |

**这就是我们的机会**：按考核要求，他们现在只有接口能跑。评审要"现场试用"时，没界面点、OCR 是假数据、`docker run` 起不来。

### 2. `parandoctor/ai-Accounting-Assistant` —— 第二个同题组，工程规范更高

🔗 https://github.com/parandoctor/ai-Accounting-Assistant

> 📌 **对应分工表**：全员（重点看 **A** 的数据层设计）· 第 1 天下午 20 分钟

**是什么**：README 自称"广东金融学院第二十一组智能体项目"，和我们**同一道题**。19 次提交、3 个 fork。
技术栈：Python 3.11+ · FastAPI + Pydantic v2 · **MySQL 8**（原生 SQL）· 大模型 OpenAI 兼容接口或 Dify · Streamlit 前端（单文件）

**它比我们骨架做得好的地方**（都是低成本可以学的决策）：

| 决策 | 它怎么做 | 为什么值得学 |
|---|---|---|
| **金额** | 存整数，单位"分"（25.00 → 2500） | 浮点累加会出现 `0.1+0.2=0.30000000000000004`，影响"刚好 100% 预算"这类边界判断 |
| **时间** | 统一存 UTC | 不依赖机器时区，换台电脑不会差 8 小时 |
| **错误响应** | 统一 `{code, message, detail}` | D 的页面处理异常只写一次，不用每个接口单独判 |
| **接口契约** | `export_openapi.py` 导出 OpenAPI | 比手写文档更不会过期 |
| **启动即建表** | 自动建库建表，并补齐缺失的列和索引 | 评审 clone 下来零配置就能跑 |
| **规则兜底** | `ai/rules.py` 独立成文件 | 和我们的 `mock_llm.py` 同一个思路——说明这么做是对的 |

**它的缺口**（README「待开发领域」原文）：

| 缺口 | 原文 |
|---|---|
| 预算页没接 | 前端单文件只覆盖记账、查账、统计；预算页待补充 |
| Docker 没联调 | 「Dockerfile 已准备，计划完成镜像构建、容器编排、环境变量与数据卷联调」 |
| 前端挤 | 三个功能区挤在一个 `app.py` 里 |

> 注意：**三个同题组（我们 + KuGua-Gu + 他们）的软肋完全一样——前端不完整、Docker 没跑通。**
> 这反过来验证了排期把 Docker 提到第 5 天做第一版是对的。

**别抄的三点**：

| 它的选择 | 为什么我们不做 |
|---|---|
| **MySQL 8** | 评审要先装 MySQL、建账号、配端口才能跑。我们 SQLite 是一个文件、零配置——**"可复现性"这一项我们反而占优** |
| **uv + pyproject.toml** | 我们的 pip + `requirements.txt` 已经跑通，换工具链等于把依赖坑重踩一遍 |
| **Dify 工作流** | 多一层外部服务，多一处出错点。OpenAI 兼容接口够用 |

> ⚠️ **红线**：同校、同题、同考试，评委很可能两边都看，甚至可能就是你认识的人。
> **只能看 README 和目录结构，一个字都不能抄。** 看的时候可以对照我们的 `app/` 想"如果重来我会怎么分层"，但不要开着它的代码写自己的。

### 3. `thedarkich/fintechathon-agent` —— 出题人的思想来源

🔗 https://github.com/thedarkich/fintechathon-agent

> 📌 **对应分工表**：**B**（prompt 设计与查账方案）+ 全员理解考核意图 · 第 1 天下午 40 分钟

**是什么**：FinTechathon 2026 银行 AI 智能体，991 个测试、55 个动作、PIN + 短信验证、微信小程序。
考核文档里那句「本题参考 FinTechathon『银行 AI 智能体』的思路」，指的就是它。

**三条设计哲学，直接决定我们的方案：**

**① AI 只规划，事实由代码陈述**
（原文：*The AI understands and plans. Fixed code decides what is allowed, and code (not the AI) states every fact.*）
→ 对应 **B 的 `parse_query()`**：**不让模型张嘴报数字**。模型只输出 `{时间段: 上月, 类别: 餐饮, 指标: 合计}`，金额由 **A 的 SQL** 去库里算。
答辩被问"怎么保证数字准"，这就是标准答案。

**② 确认卡片（confirm card）**
它的每张卡都写清：谁、多少钱、什么时候、为什么要你确认。
→ 对应 **D 的记账页 + B 的解析结果展示**：「识别结果 → 确认页 → 入库」。题目也要求"允许用户确认或修正后再入库"。

**③ 没配模型也能演示**
它有个确定性的离线规划器，没模型 Key 时接管，功能照常可用。
→ 对应 **B 的 `mock_llm.py`**。对手已经做了，我们不做吃亏。

**别抄**：991 个测试、55 个动作、权限分级、哈希链审计、微信小程序。这是几个月的工作量，**15 天里碰任何一个都会拖垮主线**。

### 5. `yiqiang310-cell/accounting-assistant` —— 和我们最像的 Python 项目

🔗 https://github.com/yiqiang310-cell/accounting-assistant

> 📌 **对应分工表**：**A** 的目录结构与建表、**B** 的意图解析 · 第 1 天下午各 1 小时

**是什么**：Python + FastAPI + SQLite + LLM 意图识别。自然语言记账、自动分类、消费分析、预算管理，四项全有，而且**就是 Python**。

**能抄的三点**：

| 抄什么 | 用在分工表哪里 |
|---|---|
| **目录怎么分**：`llm/` `handlers/` `db/` `api/` | **A** 第 1 天建文件夹骨架 |
| **建表 SQL**：`bills(...)` + `budgets(...)` | **A** 第 3-4 天的建表 |
| **意图 → Handler 的字典分发** | **B** 的 `parse_query()` + 第 9-10 天的多意图处理 |

目录长这样：
```
llm/          intent_parser.py（意图解析 prompt）
handlers/     accounting.py / query.py / budget.py / analysis.py
db/           database.py（连接）/ models.py（表）
api/          REST 路由
```

字典分发长这样：`INTENT_HANDLERS = {"add_expense": ..., "query_balance": ...}`
新增功能只加一个函数 + 注册一行，不改核心逻辑。答辩时这叫"**策略模式**"，是加分点。

**它和我们一致的地方**：也不让模型自由写 SQL，而是输出 `{intent, params}`，再由代码调函数。

**别抄**：飞书机器人、Nginx + systemd 部署、JWT 多用户。题目都不要求。

### 6. `duartedasha/AI-Powered-Expense-Tracker` —— 全链路怎么拆

🔗 https://github.com/duartedasha/AI-Powered-Expense-Tracker

> 📌 **对应分工表**：**C** 的 OCR 全流程、**D** 的页面写法 · 第 1 天下午，C 1 小时 / D 20 分钟

**是什么**：把「图片小票 → 结构化 → 入库 → 报表 → 自然语言提问」拆成 11 个独立文件。Python + SQLite + Streamlit。

**它的管线**（照着理解"一个 AI 应用长什么样"）：
```
图片 → 清洗 → OCR → LLM 抽取字段 → LLM 打分类 → 写入 SQLite → Streamlit 页面
                                          ↘ LLM 把问题转成 SQL
```

**能抄的两点**：

| 抄什么 | 用在分工表哪里 |
|---|---|
| **一条 LLM 只干一件事**（抽字段和打分类分两个 prompt、两次调用） | **B** 第 3-4 天的记账 prompt |
| **LLM 失败用正则兜底**（`ollama1.py`） | **B** 第 3 天的 `mock_llm.py` |
| `frontend1.py` 的 Streamlit 页面写法 | **D** 的页面布局 |
| `data_insertion.py` 里入库的字段清单 | **C** 判断小票要抽哪些字段 |

> **零基础最容易犯的错**：写一个巨型 prompt 让它"抽字段+分类+查账"全干，结果什么都不稳定。

**别抄**：本地 Ollama（零基础装模型会卡两天）、Tesseract 硬编码路径、OpenCV 图像预处理（用视觉大模型后不需要）。

## 五、一句话

- **两个同题对手的缺口**（他们都没做完界面，Docker 也都没跑通）
